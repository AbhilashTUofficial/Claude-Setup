# Research: core workflow model & execution engine

Sources: `packages/workflow/src/` and `packages/core/src/` in the local clone (v2.41.0). Read-only, builder's-eye view.

## Data model

- `IWorkflowBase` (`packages/workflow/src/interfaces.ts:3667-3685`) — `nodes: INode[]` + `connections: IConnections`. **Verified-in-code.**
- `INode` (`interfaces.ts:1730-1760`) carries `type`/`typeVersion`/`parameters` plus execution-behavior flags: `retryOnFail`/`maxTries`/`waitBetweenTries`, `alwaysOutputData`, `executeOnce`, `onError`/`continueOnFail`. **Verified-in-code.**
- `IConnection` (`interfaces.ts:106-115`) — `{ node, type, index }`, a directed edge to a destination. `NodeConnectionType` includes `Main` plus 11 `Ai*` types (`interfaces.ts:2965-2985`) — AI sub-node wiring reuses the same edge mechanism as ordinary data flow, but is *resolved* completely differently at runtime (see AI-agent-nodes-analysis.md).
- **The connections-indexed-by-source gotcha** — Documented directly in the repo's own `AGENTS.md:200-216`, independently Verified-in-code: `IConnections = { [sourceNodeName]: ... }`. `mapConnectionsByDestination()` (`common/map-connections-by-destination.ts:5-49`) rebuilds a destination-indexed copy. **Both orientations are the exact same TypeScript type** (`IConnections`), so nothing statically distinguishes a source-indexed map from a destination-indexed one — you have to know the convention. `getChildNodes()`/`getParentNodes()` (`common/get-child-nodes.ts`, `get-parent-nodes.ts`) are one-line wrappers around one generic traversal (`get-connected-nodes.ts:13-27`); the only difference is which map you feed it. The `Workflow` class precomputes both once at construction (`workflow.ts:65-67,144-147`) so callers using `Workflow` instance methods never hit this trap — only callers working with raw connection JSON before wrapping it do.
  - Traversal is memoized by `(depth, nodeName)` (`get-connected-nodes.ts:50-54`) — verified by a test building ~30 diamond-shaped joins (up to ~10⁹ possible paths) that still completes near-linearly (`test/get-connected-nodes.test.ts:33-50`).
  - Cycle-safe via a `currentPath` set — verified by a test with an explicit `A→B→C→A` cycle asserting the traversal returns `{B,C,D}`, never re-entering `A` (`test/get-connected-nodes.test.ts:53-68`).
  - A separate legacy static method, `Workflow.getConnectionsByDestination()` (`workflow.ts:164-207`), duplicates `mapConnectionsByDestination`'s algorithm byte-for-byte — likely dead code, not exhaustively confirmed unused (**Unconfirmed**).
- **Item data model** — `INodeExecutionData` (`interfaces.ts:1844-1867`): `{ json, binary?, error?, pairedItem?, ... }`. A node's output per connection is `INodeExecutionData[][]` — outer array = output branch, inner array = ordered items on that branch. `pairedItem` is what lets `$('Node').itemMatching()` trace an item back through branches/merges. **Verified-in-code.**

## Expressions engine

- A parameter is an expression iff the **stored string starts with `=`** (not `{{ }}` itself) — `isExpression()`, `expressions/expression-helpers.ts:5-9`. **Verified-in-code.**
- `{{ }}` interpolation is handled by **`@n8n/tournament`**, "an output-compatible rewrite of `riot-tmpl`" (Documented, its own README). Before Tournament runs, an AST rewrite pass (`extendSyntax()`, built on esprima-next+recast) rewrites n8n's proprietary chained "expression extension" methods (date/string/array/object helpers with no native JS equivalent) into calls against an injected `extend` function. **Verified-in-code**, `expression.ts:688-705`.
- Three swappable engines: `legacy` (in-process `new Function`-based Tournament), `vm` (Node-only, `isolated-vm`), `quickjs` (works in Node+browser) — set once at process startup, never mid-execution (explicit warning in the JSDoc). **Verified-in-code**, `expression.ts:221-398`.
- Sandboxing is aggressive: dangerous globals (`document`, `eval`, `Function`, `require`, `fetch`, `Promise`, `Proxy`, `Reflect`, `WebAssembly`, ...) are shadowed with empty objects; `Object`/`Error` are wrapped in `Proxy`s specifically blocking `Object.defineProperty`/`getPrototypeOf` and `Error.prepareStackTrace`/`captureStackTrace` — the latter's inline comment cites it as blocking a **known V8 sandbox-escape technique** (`expression.ts:106-218,403-558`). A regex additionally rejects any expression text containing `.constructor`. **Verified-in-code, Documented** (inline security comment).
- Context object (`WorkflowDataProxy`, `workflow-data-proxy.ts`, 1741 lines) is built from nested `Proxy`s for lazy lookup. Key surface (all `Verified-in-code`): `$json`/`$data` (current item), `$binary`, `$node` (legacy, by-name), `$(nodeName)` (modern selector: `.first()`/`.last()`/`.all()`/`.item`/`.itemMatching()`), `$input` (current node's incoming data), `$prevNode`, `$workflow`, `$parameter`/`$rawParameter`, `$runIndex`/`$itemIndex`/`$mode`, `$now`/`$today` (Luxon), `$jmesPath`, `$evaluateExpression()`, `$fromAI`.
  - **Layering point**: `$execution`/`$evaluation`/`$vars`/`$secrets` are only *typed* in `packages/workflow` (`interfaces.ts:3291-3308`) but never populated there — `packages/core`'s `getAdditionalKeys()` (`node-execution-context/utils/get-additional-keys.ts:20-56`) supplies the actual runtime values (execution id/mode, instance variables, a secrets proxy exposed **only** while resolving credential fields, gated by `options.isCredential`). **Derived**: `workflow` owns the generic mechanism, `core` injects execution/persistence-aware values — a clean package-boundary split.

## Execution engine

- `WorkflowExecute.run()` (`packages/core/src/execution-engine/workflow-execute.ts:142-211`) resolves a start node, optionally computes a partial-execution `runNodeFilter` from `workflow.getParentNodes()` (destination-indexed!) — for AI agents this also pulls in non-`main` ancestors, since "Agents use the engine to run tools through non-main connections" (inline comment, `:159-176`).
- `processRunExecutionData()` is **a LIFO work-stack machine, not a pre-computed topological scheduler** — `while (isExecutionStackNotEmpty())`, `popExecutionStack()` (`:2249-2259`). Deliberately not declared `async` (would silently break cancellation — inline comment, `:217-220`). **Verified-in-code.**
- Infinite-loop guard: repeating `${node}:${runIndex}` back-to-back throws `UserError('...endless loop')` (`:2270-2273`).
- Fan-in (a multi-input node like Merge missing a branch) — the node is skipped this iteration (`continue executionLoop`), backed by `waitingExecution` bookkeeping in the persisted execution state; exact re-queue mechanics not traced to completion (**Unconfirmed** in detail, existence confirmed).
- Retries read the node's `retryOnFail`/`maxTries`/`waitBetweenTries` and loop `runNode()` with `sleep()` between attempts (`:2302-2361`).
- **Tool-calling is not a special-cased execution path.** A node's `execute()` can return an `EngineRequest` (`{ actions, metadata }`, `interfaces.ts:2656-2661`) instead of normal output — "please run these other nodes for me" — and `handleEngineRequest()` (`:1580-1616`) folds each action back into the *same* stack via `addNodeToBeExecuted()`. AI agent tool-calling reuses this generic mechanism. **Verified-in-code** (request type + consuming code read directly; full `handleRequest()` body not read).
- `runNode()` (`:1349-1489`) dispatches purely on **which method the `INodeType` implements**: `.execute`→`ExecuteContext`, `.poll`→`PollContext`, `.trigger`→`TriggerContext`, `.supplyData` (no `.execute`)→ configuration-node path, declarative (`requestDefaults`/no `execute`)→`RoutingNode`. Each context class is what a node's code receives as `this`; all extend `NodeExecutionContext`, which `implements` a `packages/workflow`-defined shape while `packages/core` supplies the concrete implementation. **Verified-in-code** — confirmed the full class list (`ExecuteContext`, `ExecuteSingleContext`, `TriggerContext`, `PollContext`, `WebhookContext`, `HookContext`, `SupplyDataContext`, `LoadOptionsContext`, `LocalLoadOptionsContext`, `CredentialTestContext`) and their instantiation sites, though not every class body was read line-by-line.
- **Trigger activation is tracked differently per trigger kind.** Event/cron/poll triggers: **in-memory only**, per running instance, via `ActiveWorkflowTriggers` — its own doc comment states this explicitly (`active-workflow-triggers.ts:42-46`). Activation is roll-back-safe: if one trigger in a multi-trigger workflow fails to activate, already-registered ones (crons first) are deregistered (`rollbackPartialActivation()`, `:327-356`). Sub-minute poll cron intervals are rejected at activation with a `UserError` (`:382-384`). Webhook triggers are **persisted in the DB** (`webhook_entity` table) and served by `packages/cli`'s `WebhookService`, not this in-memory manager.
- `IRunExecutionData` (`run-execution-data/run-execution-data.ts`) is explicitly documented inline as existing so a failed/paused execution can be **resumed**, not just recorded — the `nodeExecutionStack` itself is part of the persisted state. Versioned (`v1`, migration path from `v0`) and brand-guarded against manual construction (must go through `createRunExecutionData`). `parentExecution`/`parentAgentRun` extend the same pause/resume idea to whole sub-executions and suspended agent tool calls.

## Error taxonomy — two distinct families, don't conflate

1. **Repo-wide backend taxonomy** (`packages/workflow/src/errors/base/*.ts`, all extend `BaseError`): `UserError` (bad input/config the builder can fix, e.g. "polling interval too short"), `OperationalError` (transient/expected, e.g. an OAuth token refresh failing), `UnexpectedError` (an internal invariant broke, e.g. corrupted ciphertext, a misconfigured node package). The deprecated `ApplicationError` is a compat shim only — "don't use it anywhere" per `AGENTS.md:227-228`, enforced by a `no-application-error` ESLint rule. **Documented** in three independent places (class JSDoc, root `AGENTS.md`, a review-rules checklist) that all agree.
2. **Node-execution-facing errors** (`NodeApiError`, `NodeOperationError`) — thrown from inside a node's own `execute()` when an external API call or node logic fails, attached to the execution's per-node error data and surfaced in the editor on the failing node (seen in `ConvertKit/GenericFunctions.ts`'s HTTP wrapper). **Unconfirmed** whether these inherit from `BaseError`/the taxonomy above or are a separate lineage — flagged in unresolved.md, not asserted.
