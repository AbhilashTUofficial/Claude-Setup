# Research: AI agent workflows — the `ai_*` connection system, node catalog, n8n Assistant

Sources: `packages/@n8n/nodes-langchain/`, `packages/@n8n/instance-ai/`, `packages/workflow/src/interfaces.ts`. All `Verified-in-code` unless marked otherwise.

## The sub-connection ("cluster node") model — n8n's most distinctive AI concept

n8n has one ordinary connection type, `main` (item-array data flow), plus **11 `ai_*` types** (`NodeConnectionTypes`, `interfaces.ts:2965-2985`: `AiAgent`, `AiChain`, `AiDocument`, `AiEmbedding`, `AiLanguageModel`, `AiMemory`, `AiOutputParser`, `AiRetriever`, `AiReranker`, `AiTextSplitter`, `AiTool`, `AiVectorStore`) that carry **live JavaScript/LangChain objects** — a configured chat-model instance, a memory buffer, a tool — rather than `INodeExecutionData[]` items.

**How it works:**
- A **sub-node** (e.g. `LmChatOpenAi`, `ToolCalculator`, `MemoryBufferWindow`) declares `inputs: []` and an `ai_*` output, and implements `supplyData()` instead of/alongside `execute()`. `SupplyData` (`interfaces.ts:2546-2551`) is `{ response: unknown; closeFunction?; ... }` — `response` is the raw object handed to the consumer.
- A **root node** (the AI Agent, `AgentV3`) declares `ai_*`-typed inputs (computed dynamically from its own parameters via an inline expression function) and pulls the live object at execution time via `ctx.getInputConnectionData(type, itemIndex)`.
- Resolution happens in the **execution engine**, not node code: `get-input-connection-data.ts:393-578` validates required connections are present and `maxConnections` isn't exceeded, then for each connected node either calls its `supplyData()` or — if it has none but declares an `ai_tool` output — auto-wraps its `execute()` via `createNodeAsTool()`, letting ordinary main-flow nodes (e.g. "Workflow as Tool") act as agent tools with no `supplyData` implementation of their own.
- **This is architecturally different from `main` data flow**: `main` connections move item arrays through the engine's async stack-and-loop machinery over possibly many iterations; `ai_*` connections resolve **eagerly, synchronously, in-process**, the moment the parent node asks — handing back objects/behavior, not data.
- n8n's own docs/node-description URLs use the term **"cluster nodes"**: one *root node* visually clustering connected *sub-nodes* around it on the canvas.
- **Nuance**: `AiAgent`/`AiChain` exist in the enum but are used only as UI hint-string arguments, never as a real `inputs`/`outputs` entry anywhere — multi-agent composition isn't done via an `ai_agent` connection. Instead a dedicated **"AI Agent Tool"** node (`AgentToolV3`) runs the same agent logic but exposes itself as an `ai_tool` sub-node (no `main` input) — this is how n8n implements the orchestrator/multi-agent pattern, confirmed by the node's own `relatedNodes` hint: "For multi-agent systems using orchestrator pattern."
- **Vector-store nodes show the model isn't a rigid binary** — a shared factory (`createVectorStoreNode()`) gives every vector-store node up to 5 operation modes selected by a parameter, and `inputs`/`outputs` *change type based on that parameter*: `load`/`insert`/`update` behave like ordinary `main`-flow nodes (+ required `ai_embedding` input); `retrieve` has no `main` connection at all, outputs `ai_vectorStore`; `retrieve-as-tool` outputs `ai_tool` directly — the vector store becomes a RAG tool an Agent can call without a separate Retriever node.

## Node catalog (`packages/@n8n/nodes-langchain/nodes/`)

- **`agents/Agent/`** — the AI Agent node, versions 1-3.1 via `VersionedNodeType`. V3 delegates to an internal `ToolsAgent`: gathers model+fallback model+memory+tools+output-parser via sub-connections, runs an iterative tool-calling loop, supports HITL-gated tools, streaming, binary passthrough, structured output via a synthetic `format_final_json_response` tool. Older versions implement now-legacy agent types (`ConversationalAgent`, `PlanAndExecuteAgent`, `ReActAgent`, `SqlAgent`, etc.) retained for backward compatibility — V3 is exclusively tool-calling.
- **`llms/`** — one chat-model connector per provider (OpenAI, Anthropic, Azure, Bedrock, Gemini/Vertex, Groq, Cohere, Mistral, DeepSeek, Ollama (local), HuggingFace, OpenRouter, xAI Grok, and more). Older non-"Chat" completion-style connectors are explicitly excluded from the Tools Agent's default model filter since that agent requires tool-calling support.
- **`memory/`** — `MemoryBufferWindow` (in-process, its own node warns it's not safe for queue/multi-main mode), plus external persistent stores (Postgres, Redis, MongoDB, Xata, Zep, Motorhead), and a `MemoryManager`/`MemoryChatRetriever` pair for inspecting/editing history outside an agent run.
- **`tools/`** — Calculator, Code (JS/Python as a tool), HTTP Request (as a tool), Wikipedia, WolframAlpha, SerpApi, SearXng, Think (a no-op reasoning-scratchpad tool), VectorStore (wraps a vector store as a retrieval tool), **Workflow** (calls another n8n workflow as a tool — a distinctive n8n-specific composition primitive).
- **`vector_store/`** — one node per backend (Pinecone, Qdrant, Weaviate, Supabase/pgvector, Redis, MongoDB Atlas, Milvus, Azure AI Search, Oracle, Databricks, Zep, in-memory), plus `ChatHubVectorStore*` variants (confirms n8n's "Chat Hub" feature has real code presence in v2.41.0, resolving the docs-angle's uncertainty there).
- **`retrievers/`, `embeddings/`, `rerankers/`, `text_splitters/`, `document_loaders/`, `output_parser/`** — the remaining RAG-pipeline sub-node families.
- **`chains/`** — fixed, non-agentic pipelines (prompt→LLM→optional parser, single pass, no tool-calling loop): Basic LLM Chain, Retrieval QA, Summarization, Information Extractor, Sentiment Analysis, Text Classifier.
- **`mcp/`** — **two opposite integrations, easy to conflate**: `McpClientTool` — n8n **as an MCP client**, connects to an external MCP server and exposes its tools as `ai_tool` connections into an Agent. `McpTrigger` — the reverse, n8n **as an MCP server**, turning the workflow itself into something other tools (e.g. Claude Desktop) can call, with a layered Protocol/Session/Transport/Execution architecture supporting SSE and Streamable HTTP, single- and Redis-backed multi-instance session storage.
- **`Guardrails/`** — a `main`-flow (not sub-node) content-safety node: `classify` (branches items to Pass/Fail, IF-node-style) and `sanitize` operations; checks include jailbreak, NSFW, PII, secret-keys, URL, keyword, topical-alignment, some deterministic and some requiring an `ai_languageModel` sub-input.
- **`ModelSelector/`** — a sub-node that itself *consumes* sub-nodes: N configurable `ai_languageModel` inputs, one `ai_languageModel` output, picks one connected model per item by IF-style rules — proof sub-nodes can chain into other sub-nodes, not just root nodes.

## "n8n Assistant" (Instance AI) — a completely separate system from the Agent node

**Documented**, from `packages/@n8n/instance-ai/CLAUDE.md` + `docs/architecture.md`. This is n8n's own embedded product assistant — a chat interface built into every instance for building/inspecting/debugging workflows, executions, credentials, data tables in natural language. **Not a workflow node**, doesn't run on the canvas.

**Critical non-conflation point (Verified-in-code)**: the canvas AI Agent node (above) is built on `@langchain/classic`/`@langchain/core`. Instance AI's orchestrator is built on a **completely separate, n8n-authored package** (`@n8n/agents`), itself on top of the **Vercel AI SDK** — no LangChain dependency found in `instance-ai`'s `package.json`. **n8n ships two independent agent runtimes in this repo**: a LangChain-based one for user workflows, a Vercel-AI-SDK-based one for its own product assistant.

Architecture highlights: a "deep-agent" pattern (explicit planning with a persisted, user-approved task graph; orchestrator-led execution rather than heavy sub-agent delegation; background Observer/Reflector agents compressing old context so the orchestrator stays bounded); a fresh orchestrator instance per request (conversation state lives externally); streaming via SSE with replay support; a small always-loaded core tool set plus a much larger deferred tool surface discovered on demand (explicitly modeled on Anthropic's own tool-search guidance for large tool sets); domain tools for workflows/executions/credentials/data-tables/nodes/research, with destructive actions (delete, publish, credential deletion) gated behind human-in-the-loop approval; credential secrets never returned to the model.

**The precise relationship** (the exact thing not to conflate): Instance AI's `build-workflow` tool compiles a workspace `.workflow.ts`/JSON source file, validates it, and saves it — meaning **Instance AI can itself build the very LangChain-based Agent/Tool/Memory graphs described above**, using node-description metadata (a `builderHint` block, e.g. `Agent.node.ts:32-166`, that documents the `subnodes: {model, memory, tool, outputParser}` wiring pattern for an LLM to follow). **Instance AI is the builder; the canvas Agent node is one of the things it can build.**
